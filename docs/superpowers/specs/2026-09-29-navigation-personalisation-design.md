# 导航个性化 + 手机端计算器键盘

日期：2026-09-29
性质：设计文档，实现前须评审
状态：**已实现**（2026-09-29，浏览器实测三端）

实现偏离设计的三处，均为实测所迫：

1. **底栏项数做成可选（3–5），不只是「选哪些」**。设计里「选哪些」由前缀顺序表达，实现时发现用户需要显式设定槽位数，否则不知道边界在哪。加了 `size` 字段 + 步进器 + 边界线。
2. **手机键盘默认收起函数页**。设计假设全键盘能放下；实测 390×844 下全键盘 574px，把输入框挤出屏幕——键盘盖住了它服务的字段。收起后 361px，输入框与结果同屏。数字、运算符、内存、`=` 不受影响。
3. **桌面编辑器改为居中对话框**。设计未指定形态，实现时先复用了手机底部抽屉，1440px 下变成横跨全屏的细条。941px 断点以上改居中 560px 对话框。

另有两处顺带修正：

- `--nav-h` token：`56px + safe-area` 原本硬编码在四处，实测差 1px（底栏 1px 边框）导致 `=` 被盖住。提为单一 token。
- `material.mjs` 的三个导出仅内部使用，取消导出；`nav.mjs` 被 `nav-order.mjs` 取代，删除（避免 `PRIMARY_TABS` 成为第二真相源）。

---

## 0. 三件事，以及为什么第三件是 bug

| # | 需求 | 性质 |
|---|---|---|
| 1 | 底栏/侧栏可自定义（选哪些 + 排序） | 新功能 |
| 2 | 拖动排序的动效 + 毛玻璃质感 | 新功能（毛玻璃一半已存在） |
| 3 | 手机端计算器弹系统输入法、占屏过大 | **缺陷** |

第 3 件不是设计取舍，是功能缺失：应用**已有**完整计算器键盘（`CalculatorDrawer` 里的 `DIGIT_KEYS` / `UNIT_KEYS` / `MEMORY_KEYS`），但只在桌面端接上；手机端「计算」面板的表达式框是 `type="text"` 且没有自定义键盘，所以点它必然弹出系统输入法，在 390×844 上占掉约一半屏幕。

## 1. 调研结论（决定方案的部分）

### 1.1 两大平台规范都反对可滑动底栏

| 来源 | 原文 |
|---|---|
| Material Design 3 | 「避免在导航栏放超过 5 项」「超过 5 项时元素会互相挤压，翻译文本也放不下」 |
| Material Design 1 | 「**避免在底部导航中使用可滚动内容**」（原文 Don't） |
| Apple HIG | iPhone 上 3–5 个；超 5 个每项宽度掉到 78pt 以下，命中变难 |
| 可用性研究（引 Fitts 定律） | 3–5 项的底栏比 6 项以上**快 20–30%** |

**所以本设计不做可滑动底栏**，改为「个性化固定底栏」——满足「所有功能可达 + 常用项可自定义」，且不违反规范。

### 1.2 业界成熟模式（Taskito / Salesforce）

- Taskito：更多 → 个性化 → 选页面 + 拖动排序。**第一项固定、更多固定最后**，最多 5 项。
- Salesforce：用户可在手机端直接重排导航项，无需管理员。

共同点：都是「**选哪些 + 排序**」，不是横向滑动。

### 1.3 拖动排序的流畅实现要点

| 要点 | 做法 | 来源 |
|---|---|---|
| 统一触摸/鼠标 | Pointer Events + `setPointerCapture` | MDN |
| 不卡（保 INP） | **FLIP**：记录旧位置 → 改 DOM → 算差值 → `transform: translate3d` 反向 → 播放 | 多源一致 |
| 帧同步 | `pointermove` 只存坐标，`requestAnimationFrame` 里才渲染 | 同上 |
| 让位动画 | **~100ms**，让用户看到放开后会怎样 | NN/g |
| 拖动阈值 | 3–5px，避免点击被误判为拖动 | SortableJS |
| 无障碍 | Enter 拿起 → 方向键移动 → Enter 放下 → Esc 取消 | Microsoft To Do |
| 减弱动效 | CSS 与 JS **双保险**检查 `prefers-reduced-motion` | MDN |

### 1.4 毛玻璃：一半已存在，底栏漏在外面

应用已有完整的毛玻璃系统（`--chrome` 半透明 token、`@supports` 渐进增强、无 blur 时回退纯色）。但：

- `.mobile-nav` **不在** `[data-material="frosted"]` 覆盖列表里
- 它自己写了一条 `backdrop-filter: blur(12px)`，在 `@supports` 块**外**——所以纯色模式下也在模糊（白费性能），且缺 `saturate(180%)`，与顶栏/侧栏不一致

**这一条已在本轮修复**（见提交记录），并加了 `test/material.test.mjs` 守住。

性能约束（来自实测文章）：
1. **一屏只用一块玻璃面**，不是六块
2. **绝不动画化模糊半径**——每帧重算整条滤镜链
3. 玻璃不要盖在长滚动区上

## 2. 设计

### 2.1 数据模型：一份偏好，两端共用

```
lab-calc.nav.v1 → { order: string[] }   // 全部 20 个页签 id 的顺序
```

**为什么存全量顺序而不是「底栏那 5 个」**：桌面侧栏要显示全部 20 项，手机底栏只显示前 5 项 + 更多。存一份全量顺序，两端读同一份数据——用户在手机上把「分光光度」拖到第一位，换到电脑上侧栏也是第一位。存两份会让它们漂移。

派生规则（纯函数，可测）：
- 手机底栏 = `order.slice(0, 5)` + 「更多」
- 手机「更多」面板 = `order.slice(5)`
- 桌面侧栏 = 全部 `order`

**存储层复用 `history.mjs` 的模式**：注入 store、`memoryStore` 供测试、`localStorage` 不可用时降级内存。

### 2.2 纯函数层：`src/ui/nav-order.mjs`

```
export const NAV_STORAGE_KEY = 'lab-calc.nav.v1';
export const DEFAULT_ORDER = [...];        // 现有的 20 项顺序
export function loadOrder(store, allIds)   // 读 + 校验 + 补新增/删已删
export function saveOrder(store, order)
export function moveItem(order, from, to)  // 拖动排序的纯计算
export function barTabs(order, n = 5)      // 底栏前 n 项
export function moreTabs(order, n = 5)     // 其余
```

**`loadOrder` 必须容错**：存储里的 id 可能已不存在（页签改名/删除），也可能缺少新页签。规则：
- 存储里有但已不存在的 id → 丢弃
- 存在但存储里没有的 id → 追加到末尾（按默认顺序）
- 结果为空 → 返回 `DEFAULT_ORDER`

这一条是必需的：升级后新增页签若被丢掉，用户会发现「新功能不见了」。

### 2.3 组件层

| 组件 | 职责 |
|---|---|
| `NavOrderContext.jsx` | 提供 `order` + `setOrder`，写存储 |
| `NavEditor.jsx` | 编辑面板：勾选 + 拖动排序 + 恢复默认 |
| `useDragReorder.js` | 拖动逻辑（Pointer Events + FLIP），供编辑器复用 |

`NavRail` / `MobileNav` 改为从 context 读顺序，不再直接读 `PRIMARY_TABS`。

### 2.4 拖动排序的实现

```
pointerdown  → 记录起点，等移动超过 4px 才认定是拖动
pointermove  → 只更新坐标；rAF 里做视觉更新
             → 跨过邻居中点时交换顺序，邻居用 FLIP 让位（100ms）
pointerup    → 落定，写存储
```

**无障碍**：每项有拖动手柄按钮，`aria-grabbed` 标记状态；键盘 Enter 拿起 → 方向键移动 → Enter 放下 → Esc 取消并还原。屏幕阅读器播报「称量配制，第 2 项，共 6 项」。

### 2.5 手机端计算器键盘

「计算」面板的表达式框改 `readOnly`，点击不弹系统输入法；下方接上已有的 `.calc-keypad`。

键高 **40 → 44px**（触控下限），键盘吸底，结果区悬在上方。安全区适配（`env(safe-area-inset-bottom)`）。

**桌面端不动**——它现在工作良好，抽屉形态与手机的内嵌形态是两种场景。

### 2.6 动效

| 位置 | 动效 | 时长 |
|---|---|---|
| 拖动让位 | FLIP `translate3d` | 100ms（NN/g 建议） |
| 底栏选中态 | 指示器滑动 | 200ms |
| 按下反馈 | `scale(0.96)` | 120ms |
| 编辑面板进出 | 高度 + 淡入 | 200ms |

全部走 `--dur-*` token，全部受 `prefers-reduced-motion` 约束。

## 4. 不做的事

- **可滑动底栏**（违反 M3/HIG，实测慢 20–30%）
- **自定义显示名**（无法翻译）
- **按使用频率自动排序**（用户无法主动控制）
- **改动桌面端计算器抽屉**（现在工作良好）

---

## 5. 风险

| 风险 | 缓解 |
|---|---|
| 拖动在低端机上掉帧 | FLIP + `translate3d` 走 GPU 合成层；`pointermove` 不在事件里做布局计算 |
| 升级后用户顺序错乱 | `loadOrder` 容错规则（见 2.2） |
| 编辑面板太复杂 | 只做「勾选 + 拖动」两件事，不做嵌套分组 |
| 键盘接上后布局挤压 | 键高 44px 后仍超出则键盘内滚动；实测 320px 宽 |
