## 1. 问题陈述

用户提出的原话是四条：界面不对称、美术和艺术性不够、需要新功能、README 要重写。
前三条各是一类问题，不是一条。分开陈述，因为它们的证据形式不同。

### 1.1 界面不对称（已实测，是缺陷不是偏好）

在 1440×900 与 1920×1080 两个视口实测：

| 元素 | 1440px | 1920px |
|------|--------|--------|
| 卡片宽度 | 849px | 904px |
| 表单列宽（计算前） | 560px | 560px |
| **右侧死区** | **289px** | **319px** |
| 化学式字段宽 | 327px | 327px |
| 其下 `.row` 内字段宽 | 560px | 560px |
| 卡片高 | 700px | 700px |
| 表单内容高 | 287px | 287px |
| **底部死区** | **约 400px** | **约 400px** |

计算之后变成 388/388 两列，对称。

**根因**是三条规则互相作用：

1. `.field { max-width: max(220px, 34ch) }` — 单字段被限制在 327px
2. `.row .field { max-width: none }` — 行内字段不受限，撑到 560px
3. `@container card (min-width: 620px) { .card:not(:has(> .card-results)) > .card-main { max-width: 560px } }`

第 3 条的注释写明它的存在理由：在 1920px 下曾经出现「220px 输入框配 894px 按钮，
像两套不相关的布局叠在一起」。**这个判断是对的**，但用「限制整列宽度」来解决，
代价就是上表的死区，以及同一张卡里 327px 与 560px 两种字段宽度并存。

### 1.2 视觉系统不统一（观感问题，需主观判断）

**先纠正一处我自己的误判**：起初以为「卡片只有 `--shadow-1` 一级」，
实测不成立——`--shadow-1/2/3` 三级都已定义且都在用（卡片 `-1`、
悬停 `-2`、浮层 `-3`）。**层次机制已存在**，不是缺失项。

所以这一节剩下的问题更窄：

- 结果主数字与标签的字号对比不足，主次不分（这是观感判断，非缺陷）
- 间距已 token 化（`--s1`…`--s6` = 4/8/12/16/20/24px），圆角
  `--r-sm/md/lg` = 6/10/14px 已定义，但**存在硬编码值绕过 token** 的规则

**再纠正一处**：初稿写「存在硬编码值绕过 token」，未给数量。实测量化后：

| 硬编码值 | 出现次数 | 性质 |
|---------|---------|------|
| 1px | 8 | 发丝线，**不是间距**，应保留 |
| 2px | 21 | 微调（图标对齐等），应保留 |
| 3px | 15 | 同上 |
| 4px | 2 | **真绕过**（应走 `--s1`） |
| 5px | 2 | **真绕过**（不在刻度上） |
| 6px | 4 | **真绕过**（应走 `--s2` 或 `--r-sm`） |
| 8px | 2 | **真绕过**（应走 `--s2`） |
| 15px | 1 | **真绕过** |
| 26px | 1 | **真绕过** |

合计 56 处，其中 **46 处是 1–3px 的发丝线与微调，属正当用法**。

**第三次订正（实现阶段实测）**：那「10 处」也不是全部该清理。逐条查
上下文后发现，其中 6 处（`gap: 6px` / `gap: 8px`）位于
`@media (max-width: 639px), (pointer: coarse) and (max-height: 500px)` 内，
是**窄屏与触屏的计算器键盘**——10 列网格，6px 是为了塞下按键而选的，
换成 `--s2`(8px) 会挤坏布局。这属于**刻意偏离刻度**，不是疏忽。

真正可议的只剩 4 处（`padding-right: 26px` 是下拉箭头留白、
`padding: 15px 0 14px` 是图例轨道、两处 `padding: 1px 5px` 是 kbd 标签），
且每一处都有具体理由。

**结论（订正后）**：视觉部分几乎没有「清理硬编码」这项工作量。
token 体系本身是干净的，偏离处都是有理由的。

**第四次订正（字阶实测）**：初稿写「结果主数字与标签的字号对比不足，
主次不分」。浏览器实测：

| 元素 | 字号 | 字重 | 颜色 |
|------|------|------|------|
| 主数字 | 34px | 650 | accent |
| 单位 | 16px | 450 | text-dim |
| 结果网格标签 | 11.5px | 400 | text-dim |
| 结果网格值 | 14.5px | 600 | text-mid |

主数字是标签的 **2.96 倍**，且只有它用 accent 色。**层级是清楚的，
这条也不成立。**

**视觉部分的真实结论**：初稿列的三项（阴影层级、硬编码、字阶）经实测
**全部不成立**。token 体系、层次机制、字阶对比都已经是好的。

那「美术不够」的感受从哪来？只剩下**装饰与品牌**——即用户明确要的
「装饰性元素」与「首屏/品牌形象」。这不是修复，是新增。
本版据此调整范围：视觉部分只做新增项，不做无谓的「清理」。

### 1.3 缺失的能力（对照竞品与自家路线图）

BioQuant PCR 等工具。结论分两类：

**已有，不需做**（避免重复劳动）：

- **操作步骤流程图**：把「取多少→加多少→定容到多少」画成可导出 SVG 的流程图

## 2. 已确立的设计约束

这些不是选择，是既成事实，任何方案都必须满足：

1. **位图不可用。** 应用有 10 套主题 + 明暗切换。PNG/JPG 插图无法跟随主题变色，
   浅色主题下会变成脏斑。只有 SVG（`currentColor` / CSS 变量上色）可用。
   ——来源：对 SVG 主题化的调研（CSS custom properties + `currentColor` 是标准做法）
2. **10 个标签页已有图表。** BioTab / BufferTab / CurveTab / ElectroTab / ElementsTab /
   PhTab / PhysicalTab / ReactionTab / SeriesTab / SpectroTab 已绘制图表。

4. **主题化已就位。** `.diagram-axis line { stroke: var(--border-strong) }` 等规则
   已全部使用 CSS 变量，图表自动跟随 10 套主题。
5. **MIT 授权。** `scripts/check-licences.mjs` 强制 allow-list（MIT/ISC/Apache-2.0/
   BSD/CC0/OFL/CC-BY-4.0）。GPL/AGPL/CC-BY-SA 拒绝。
6. **不确定度路径已经正确。** 7 个标签页走 `roundPair`，精度一致性问题已在
   本次会话修复（commit 40c8eb0）。**不得改动这 7 个标签页的精度逻辑。**

## 3. 方案与取舍

### 3.1 不对称的修法（三选一）

| 方案 | 做法 | 取舍 |
|------|------|------|
| **A. 表单铺满（选定）** | 计算前表单占满卡片，计算后分两列 | 空白消失；布局随状态变化，但这正是当前行为且合理 |
| B. 始终两列 | 计算前右列显示占位提示 | 从一而终；但空状态下右列仍是空的，未解决根本 |
| C. 表单居中收窄 | 保持窄表单，水平居中 | 视觉对称；牺牲可用宽度，长公式会挤 |

**选定 A**，理由：空白是「无内容的区域」，而 A 消除它；B 只是把空白换成占位文字。

**具体做法（已在浏览器原型验证，见下）**：约束的落点从「列」移到「卡片自身」——
让卡片按内容收窄，而不是让字段在一张过宽的卡里留白。

原型实测（1440×900，注入临时样式后量测，非推断）：

| 变体 | 卡片宽 | 顶层字段 | 行内字段 | 右侧死区 |
|------|--------|---------|---------|---------|
| 现状 | 849px | 327px | 560px | 289px |
| 变体 A：仅解除列上限 | 849px | 799px | 392px | 25px |
| 变体 B：字段统一 560px | 849px | 560px | 272px | 25px（但卡内仍空 239px） |
| **变体 C：卡片按内容收窄** | **612px** | **563px** | **273px** | **25px** |

**选定变体 C**。变体 A 是错的——它把输入框拉到 799px，正是原先 560px
上限要防的事（原注释：「220px 输入框配 894px 按钮，像两套不相关的布局
叠在一起」）。变体 B 字段对齐了，但卡片仍留 239px 空。只有 C 同时
满足三点：字段同宽、无死区、按钮不成为一条长带。

代价：卡片在窄屏与宽屏都不再等宽于历史栏。这是「按内容定宽」的正常
结果，但需在实现时确认与历史栏的视觉关系仍然成立。

### 3.2 视觉系统的修法

不动内容，只动 token 与规则：

- **层次**：`--shadow-1/2/3` 三级（静态卡片 / 悬停 / 浮层）
- **字阶**：结果主数字与标签的对比拉大；主数字是主角
- **节奏**：清除硬编码间距/圆角，一律走 token
- **动效**：统一缓动函数（已有 `--dur-move-*` 350/500/650ms 与
  `--dur-fx-*` 120/200/300ms 两套时标）

**依据**：Tufte 的 data-ink 原则——「Erase non-data-ink」。当前 289px 死区与
400px 底部空白正是 non-data-ink，1.1 节的修法同时是视觉改善。

### 3.3 三项能力的做法

**批量缩放**
- 纯函数 `scaleInputs(inputs, factor)`：只缩放带量纲的数值字段
- 新增记录而非覆盖原记录，并在 `meta` 标注来源（符合 ALCOA「Original」原则，
  与既有的删除用 tombstone 而非抹除一致）
- 缩放系数：0.25 / 0.5 / 2 / 5 / 10

**有效数字显示**
- **只覆盖 13 个无不确定度的标签页**，7 个有不确定度的不动（它们已正确）
- 默认开启，设置中可关
- **注意（自查发现）**：既有的 `significantFigures({ value, unc })` 在
  `unc === 0` 时返回 `null`，即它**依赖不确定度**，不能直接用于这 13 个标签页。
  需要新增一条独立路径：由输入值的精度推断结果的有效位数（乘除取最少位数、
  加减取最末位）。这是本次唯一需要新写的数值逻辑，必须先写失败测试。

**操作步骤流程图**
- 复用 `Diagram` 原语绘制流程条
- 导出走已就绪的 `serializeDiagram`（`svg-export.mjs`），无需新代码

## 5. 错误处理

- 批量缩放：因子非正数或输入不可解析 → 抛 `CalcError`，不静默产出
- 有效数字：无法确定时退回现有固定位数显示，不显示错误值
- 布局：窄屏（≤700px）走既有 media query 路径，不引入新的断点
